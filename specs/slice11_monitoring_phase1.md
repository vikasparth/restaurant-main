# Spec — Slice 11: AI Monitoring Agent Phase 1 (Rule-Based)

## Goal
A scheduled background job that checks three key health metrics twice daily. When a
problem is sustained across two consecutive windows, it opens a GitHub Issue (primary
record) and sends an owner email with a link to the issue. Silent when healthy.

---

## Schedule
- **Times:** 9:00 and 21:00 `America/Los_Angeles`
- **Trigger:** cron-job.org calls `GET /api/internal/monitor` — no APScheduler needed
- **Why not APScheduler:** Render free tier spins down after 15 min inactivity; an in-process scheduler would die with it. cron-job.org wakes the server via HTTP and scales forward to Phase 2/3 MCP approach without any rearchitecting.

---

## Metrics

Each metric is evaluated over **two consecutive windows** of `MONITOR_WINDOW_HOURS` (default 6h).

| Name | Window 1 | Window 2 | Alert condition |
|---|---|---|---|
| `error_rate` | last 6h | prior 6h (6–12h ago) | breached in both windows |
| `p95_latency_ms` | last 6h | prior 6h | breached in both windows |
| `notification_failures` | last 6h | prior 6h | breached in both windows |

**Alert fires only if at least one metric breaches in both windows.** A single-window spike → no alert.

---

## Thresholds (all configurable via env vars)

| Config field | Env var | Default | Unit |
|---|---|---|---|
| `monitor_window_hours` | `MONITOR_WINDOW_HOURS` | `6` | hours |
| `monitor_error_rate_threshold` | `MONITOR_ERROR_RATE_THRESHOLD` | `0.05` | fraction (5%) |
| `monitor_latency_p95_threshold_ms` | `MONITOR_LATENCY_P95_THRESHOLD_MS` | `2000` | milliseconds |
| `monitor_notification_failure_threshold` | `MONITOR_NOTIFICATION_FAILURE_THRESHOLD` | `2` | count |

---

## Data sources

| Metric | Table | Key columns |
|---|---|---|
| Error rate | `request_logs` | `status_code`, `created_at` |
| p95 latency | `request_logs` | `duration_ms`, `created_at` |
| Notification failures | `notification_logs` | `success`, `created_at`, `provider` |

> **Note:** `notification_failures` only alerts on rows that were attempted and failed.
> When `NOTIFICATIONS_ENABLED=false`, no sends are attempted → no rows written → metric stays 0 → no false alert.

---

## Alert flow

### On breach (at least one metric breaching in both windows)

1. **Open a GitHub Issue** (primary record)
   - Title: `[ALERT] Aap ki Rasoi — N issue(s) detected`
   - Body: metric details with window values and thresholds
   - Label: `monitoring-alert`
   - If an open issue with label `monitoring-alert` already exists → skip creation (avoid duplicates)

2. **Send owner email** (notification)
   - Subject: `[ALERT] Aap ki Rasoi — N issue(s) detected`
   - Body: same metric details + "View issue: <GitHub Issue URL>"

### On healthy (all metrics clear)

- If an open `monitoring-alert` issue exists → close it automatically
- No email sent (silent = good news, zero cost)

---

## GitHub Issue body format

```
## Monitoring Alert — 2026-04-14 21:00 Pacific

### Breaching metrics

| Metric | Window 1 | Window 2 | Threshold |
|---|---|---|---|
| Error rate | 8.2% | 7.1% | 5% |
| p95 latency | 2400ms | 2200ms | 2000ms |

### Healthy metrics
- Notification failures: 1 / 0 (threshold: 2) ✓

---
*Auto-generated by monitoring agent. Will be closed automatically when metrics recover.*
```

## Internal endpoint

`GET /api/internal/monitor`

Protected by `X-Internal-Token` header (same as `/send-reminders`).

Response shape:
```json
{
  "checked_at": "2026-04-14T21:00:00",
  "window_hours": 6,
  "metrics": {
    "error_rate": {
      "window_1": 0.082,
      "window_2": 0.071,
      "threshold": 0.05,
      "breaching": true
    },
    "p95_latency_ms": {
      "window_1": 2400,
      "window_2": 1800,
      "threshold": 2000,
      "breaching": false
    },
    "notification_failures": {
      "window_1": 1,
      "window_2": 0,
      "threshold": 2,
      "breaching": false
    }
  },
  "alerts_fired": true
}
```

`breaching: true` means threshold exceeded in **both** windows.

## Function signatures

```python
# monitor_service.py

async def collect_snapshot(db, window_hours: int) -> dict:
    """Query DB for both windows. Returns raw metric values per window."""

async def check_thresholds(snapshot: dict) -> list[dict]:
    """Compare snapshot values against settings thresholds.
    Returns list of breaching metric dicts (empty list = all healthy)."""

async def open_or_update_github_issue(breaching: list[dict], snapshot: dict) -> str:
    """Open a GitHub Issue if none open. Returns the issue URL."""

async def close_github_issue() -> None:
    """Close the open monitoring-alert issue if one exists."""

async def run_monitor(db) -> None:
    """Collect snapshot, check thresholds, open/close issue, send email. Never raises."""
```

## Out of scope for this slice
- No WhatsApp alerts — GitHub Issues + email covers monitoring needs at zero variable cost
- No Claude API calls (Phase 2)
- No MCP tools (Phase 3)
- No per-endpoint breakdown — aggregate metrics only
- No memory/CPU metrics (Render dashboard covers those)
